Версия 1.0 (19.10.2026). Машиночитаемое описание — файл OpenAPI 3.1. CRM отдаёт его по адресу `/api/docs` (Swagger UI) и `/api/docs/openapi.json` / `.yaml`, а в репозитории он лежит в `docs/openapi/1c-integration.json` / `.yaml`. Если это руководство расходится с OpenAPI, верен OpenAPI: автоматический тест сверяет его с кодом. Английская версия: `docs/integration-1c.md`.

## 1. Архитектура: только pull

```
          push: каталог, остатки, контрагенты, оплаты
  1С  ───────────────────────────────────────────▶  API CRM  /api/v1/integration/1c
      ◀───────────────────────────────────────────
          pull: клиенты для создания, документы (заказы, счета,
          реализации с серийными номерами, оплаты, поступления) + подтверждение
```

- **CRM никогда не подключается к 1С.** Любой обмен начинает 1С: `HTTPСоединение` и регламентное задание.
- **1С отправляет (push):**
  - единицы, группы и номенклатуру (с ценами и кодами);
  - склады и остатки с себестоимостью;
  - своих контрагентов-клиентов;
  - оплаты, проведённые в 1С.
- **1С забирает (pull):**
  - клиентов, созданных или изменённых в CRM;
  - документы из исходящей очереди CRM.

  Каждую запись 1С **подтверждает** (ack): CRM сохраняет GUID и номер 1С и больше её не выдаёт.
- **Каталог и остатки обрабатываются в очереди.** CRM сразу отвечает `202` и обрабатывает данные в фоне; результат — `GET /batches/{batch_id}`. Клиенты и оплаты обрабатываются синхронно.

Базовый адрес: `https://<хост-crm>/api/v1/integration/1c`. В рабочей среде нужен только HTTPS.

## 2. Доступ

### 2.1 Токен

Администратор создаёт токен в **CRM → Настройки → Интеграции → Токены**:
1. Указывает название, например «1С рабочая».
2. Отмечает права (только нужные).
3. При необходимости указывает IP-адреса или CIDR сервера 1С.
4. Задаёт срок действия (по умолчанию 180 дней, максимум 365).
5. Включает «секрет подписи», если 1С подключается через интернет.

Токен (`1c_` + 48 символов) и секрет показываются **один раз**. Храните их в 1С в защищённом месте: в константе, видимой только администраторам, или в `БезопасноеХранилищеДанных`. Консольной команды для токенов нет — используется интерфейс. Перед окончанием срока создайте новый токен, переключите на него 1С, затем отзовите старый.

| Право | Разрешает |
|---|---|
| `items:write` | `POST /items`, раздел `items` в `POST /batch` |
| `stock:write` | `POST /item-stock`, раздел `stock` в `POST /batch` |
| `batches:read` | `GET /batches/{id}` |
| `customers:read` | `GET /customers/pending` |
| `customers:write` | `POST /customers/ack`, `POST /customers` |
| `orders:read` | лента `orders` (заказы, счета, договоры, реализации) |
| `payments:read` | лента `payments` |
| `warehouse:read` | лента `warehouse` (поступления) |
| `payments:write` | `POST /payments` |
| `warehouse:write` | `POST /goods-receipts`, `PUT /goods-receipts/{crm_id}` (приходы, созданные в 1С) |

В каждом запросе передаётся заголовок `Authorization: Bearer 1c_...`. Желательно передавать и `X-Request-Id: <uuid>`: он возвращается в поле `request_id` и виден в журнале интеграции CRM.

### 2.2 Белый список IP

Если у токена задан список адресов, запросы с других адресов получают `403 ip_not_allowed`.

### 2.3 Подпись запроса (HMAC-SHA256)

Подпись обязательна:
- для запросов не из частной сети (то есть не из 10/8, 172.16/12, 192.168/16, loopback и не из диапазонов, указанных в CRM);
- всегда — для токенов, выпущенных с секретом подписи.

```
X-Timestamp: 1760865000                       ← Unix-время в секундах (UTC), допуск ±300 с
X-Signature: sha256=<hex>                      ← hex в нижнем регистре
<hex> = HMAC_SHA256(ключ = секрет подписи, сообщение = X-Timestamp + "." + тело)
```

- Тело — ровно те байты, которые отправляются (JSON в UTF-8, **без BOM**). Для GET тело пустое, то есть сообщение равно `"1760865000."`.
- Сериализуйте JSON один раз и отправляйте ту же строку, которую подписали.
- Синхронизируйте часы сервера (NTP). Неверное время даёт `401 invalid_signature`.

## 3. Рекомендуемое расписание

| Задание | Частота | Метод |
|---|---|---|
| Остатки (изменения) | каждые 5–10 мин | `POST /item-stock` (`mode=delta`) |
| Изменения каталога | каждые 15 мин и при изменении | `POST /items` (`mode=delta`) |
| Полный снимок остатков | ночью (03:00) | `POST /item-stock` (`mode=full`, частями) |
| Полный снимок каталога | раз в неделю | `POST /items` (`mode=full`) |
| Клиенты из CRM | каждые 5 мин | `GET /customers/pending` → создать или обновить в 1С → `POST /customers/ack` |
| Клиенты, изменённые в 1С | каждые 15 мин | `POST /customers` |
| Документы из CRM | каждые 2–5 мин по каждой ленте | `GET /outbox/pending?feed=orders|payments|warehouse` → провести в 1С → `POST /outbox/ack` |
| Банк / касса | каждые 15 мин | `POST /payments` |
| Проверка связи | раз в час | `GET /ping` |

Ограничение — **60 запросов в минуту на токен**. В разделе Настройки → Интеграции CRM показывает время последнего обмена по каждой ленте и предупреждает об устаревании (каталог — 24 ч, остатки — 30 мин).

## 4. Первичная загрузка по шагам

Перед началом администратор включает «Приём из 1С» и «Обмен клиентами» в разделе Настройки → Интеграции. До этого API отвечает `503 integration_disabled`.

1. **Проверка связи:** `GET /ping`. В ответе — права токена и `integration_enabled: true`.
2. **Единицы измерения:** `POST /items` только с массивом `units`. Код — по ОКЕИ (796 шт, 166 кг, 006 м, 112 л). Точность количества CRM определяет по коду; для неизвестного кода CRM выдаёт предупреждение, и точность задаётся вручную.
3. **Группы номенклатуры:** `POST /items` с массивом `groups`. Родители — раньше потомков (или всё в одном пакете).
4. **Номенклатура:** `POST /items` с массивом `items`, не более 1000 записей и 10 МБ в пакете. Передавайте цены, коды (`accountant_code`, `class_code` ИКПУ, `package_code`) и `is_serialized`.
5. **Склады:** `POST /item-stock` с массивом `warehouses`, полем `as_of` и `stock: []`.
6. **Остатки:** полный снимок — `mode: full`, один `snapshot.id` для всех частей, `part` от 1 до N, `total_parts` = N.
7. **Клиенты:**
   1. Отправьте контрагентов через `POST /customers` (до 200 в запросе). Сопоставление идёт **только по ИНН** (ред. 4): партнёр CRM с тем же ИНН обновляется и связывается; `crm_id` и GUID для сопоставления не используются.
   2. Затем заберите `GET /customers/pending` и подтвердите.
8. **Проверка пакетов:** `GET /batches/{batch_id}` → `status: processed` (или `partial` со списком отклонённых записей).
9. **Включите регламентные задания** из раздела 3.

Для первичной загрузки из файла администратор CRM может импортировать номенклатуру с GUID 1С (Настройки → Импорт данных). Основной путь — API.

## 5. Соответствие данных

### 5.1 Общие правила

| Тема | Правило |
|---|---|
| Идентификаторы | GUID ссылки 1С (`Ссылка.УникальныйИдентификатор()`) в полях `id` / `*_id`; регистр не важен. Собственные идентификаторы CRM — UUID (`crm_id`). |
| Даты | `ГГГГ-ММ-ДД`. Дата-время — ISO 8601; без смещения читается как время Ташкента. |
| Деньги | **Строка** с десятичной точкой в основных единицах: `"1500000.00"`. Округление до 2 знаков (half-up). CRM хранит суммы в тийинах или центах. |
| Валюта | ISO 4217: `UZS`, `USD`, `EUR`, `RUB`. |
| НДС | Процент строкой: `"12"`, `"0"` или `"exempt"` (без НДС). CRM хранит базисные пункты (12 % = 1200). |
| Количество | Строка, до 3 знаков после точки: `"12.500"`. Отрицательный остаток допускается. |
| Удаление | `is_deleted: true` (пометка удаления). CRM деактивирует запись, физически ничего не удаляется. |
| Порядок | `updated_at` записи. Более старая версия не перезаписывает новую (результат `stale`). |

В CRM на один ИНН — одна **организация** с ролями клиент / поставщик / перевозчик. Этот обмен охватывает **только клиентов**. Колонки для обмена поставщиками и перевозчиками в CRM подготовлены, но не активны: методов для них пока нет.

### 5.5 Документы, которые 1С забирает из CRM

Суммы — строками, в валюте документа. Номенклатура указывается GUID 1С (`item_id`) и кодами. Клиент — полями `customer.external_id` (ваш GUID) и `customer.crm_id`.

| Событие | Лента | Что создать в 1С (предложение) |
|---|---|---|
| `order.confirmed` / `order.cancelled` / `order.closed` | orders | Заказ клиента (создать / отменить / закрыть) |
| `invoice.issued` (проформа) | orders | Счёт на оплату покупателю |
| `invoice.registered` (счёт-фактура, ЭСФ) / `invoice.voided` | orders | Счёт-фактура выданный / отмена |
| `agreement.signed` / `agreement.terminated` | orders | Договор с контрагентом |
| `delivery.posted` | orders | Реализация товаров и услуг; в `lines[].serials` — отгруженные серийные номера |
| `payment.recorded` / `payment.refund_recorded` / `payment.voided` | payments | Поступление / возврат денежных средств |
| `goods_receipt.posted` | warehouse | Приходы от поставщиков: дополните свой документ (`onec_document.id`) принятыми / повреждёнными количествами; возвраты и начальные остатки: Оприходование / возврат от клиента (`source_type`) |
| `goods_receipt.cancelled` | warehouse | Приход из 1С, отменённый в CRM (заведующим складом) |
| `stock_off.posted` | warehouse | Списание товаров (акт списания / порчи: `reason`, количества, оценочная стоимость; для повреждений при приёмке — ссылка на приход) |
| `service_ticket.closed` | orders | Реализация услуг (ремонт вне гарантии: работы и запчасти) |

События ленты orders по клиенту, которого в 1С ещё нет (у него нет GUID), придерживаются, пока этот клиент не будет подтверждён. События одного документа выдаются строго по порядку: следующее появится только после подтверждения предыдущего.

> **Партнёры (2026-10-19).** CRM теперь хранит каждую организацию как *партнёра* с ролями (клиент, поставщик, перевозчик). Эндпоинты `/customers`, права, поля и фиды работают как раньше и охватывают только партнёров с ролью клиента. Поставщики и перевозчики не передаются. Для 1С ничего не меняется.

> **Доверенность (2026-10-19).** Данные заказа, счёта и накладной содержат `power_of_attorney {required, received, received_at, note, overridden}`; CRM регистрирует счёт-фактуру только после получения доверенности (или разрешения без неё). Оплаты, записанные в CRM по заказам, по-прежнему дают событие `payment.recorded`; это сигнал для склада, учёт ведётся в 1С.

## 6. Регулярный обмен

### 6.1 Push (каталог, остатки)

```
POST /items | /item-stock | /batch
{ "batch_id": "<новый uuid>", "mode": "delta" | "full", "sent_at": "...", ... }
→ 202 { "status": "queued", "accepted": n, "rejected": [], "status_url": "..." }
→ 207 то же, плюс "rejected": [{ section, index, id, errors[] }]
→ 422 ошибка конверта или все записи неверны (ничего не сохранено)
```

- **Delta** меняет только то, что передано.
- **Full** передаёт всё целиком, частями с одним `snapshot.id`. Когда придёт последняя часть (в пределах 120 минут), не переданные активные записи деактивируются (каталог) или удаляются (остатки).
- **Защита:** если в снимке оказалось меньше 80 % активных строк, ничего не удаляется, и снимок получает статус `partial`. Снимок остатков можно ограничить складами через `snapshot.scope.warehouse_ids`.

### 6.2 Клиенты в обе стороны

1. `GET /customers/pending?limit=100&cursor=0` возвращает `data[]`, `next_cursor` и `has_more`. Повторяйте с `cursor=next_cursor`, пока `has_more` равно true.
2. По каждой записи найдите контрагента по `external_id` (если он есть) или создайте нового. Сохраните `crm_id` в 1С, например в дополнительном реквизите.
3. Отправьте подтверждение по каждой записи:
   - `{crm_id, outbox_id, status: "synced", external_id, external_code, contacts: [{crm_id, external_id}]}`, или
   - `{crm_id, outbox_id, status: "failed", error: {code, message, fields}}`.

   Текст ошибки увидит пользователь CRM.
4. Пока записи не подтверждены, они остаются в очереди. После сбоя вы просто получите их снова (`delivery_count` растёт).

### 6.3 Документы

1. `GET /outbox/pending?feed=orders&limit=200&cursor=0`.
2. Обрабатывайте события по порядку `sequence`.
3. Подтверждайте: `{event_id, result: "applied", onec_guid, onec_number, posting_status: "posted", updated_at}` — или `result: "rejected"` с массивом `errors`.
4. Если документ позже распроведён или удалён в 1С, отправьте ещё одно подтверждение по тому же `event_id` с новым `posting_status` и более поздним `updated_at`.

### 6.4 Оплаты

`POST /payments`. Поля:
- `id` — GUID документа 1С;
- `customer_id` — GUID контрагента;
- `amount`, `currency`, `paid_on`, `reference_number`, `purpose`;
- необязательно — `allocations: [{order_crm_id, amount}]`.

| Результат | Значение |
|---|---|
| `created` | новая оплата |
| `unmatched` | клиент не найден, сопоставит бухгалтер |
| `possible_duplicate` | совпадают сумма, дата и номер с уже существующей оплатой |
| `updated` / `corrected` | изменения применены |
| `voided` | передано `is_deleted: true` |
| `unchanged` | изменений нет |

### 6.5 Приходы товаров (push из 1С)

Приходы от поставщиков создаются **только в 1С** (Spec 06, раздел 21.11). 1С передаёт каждый приход; кладовщик в CRM вводит фактически принятое (принято, повреждено с комментарием, серийные номера), отмечает приход проверенным и проводит. Результат проведения доступен 1С для получения из ленты `warehouse` (`goods_receipt.posted`, по умолчанию без серийных номеров). Возвраты клиентов и начальные остатки по-прежнему создаются в CRM.

```
POST /goods-receipts                        (право warehouse:write)
{ "batch_id": "<uuid>", "sent_at": "...", "receipts": [ {
    "id": "<GUID документа 1С>", "number": "ПТ-000318", "date": "2026-10-19",
    "updated_at": "2026-10-19T09:58:00+05:00",       // необязательно, для проверки устаревания
    "crm_id": null, "version": null,                 // присылайте, когда они у вас есть
    "warehouse_id": "<GUID склада 1С>",
    "supplier": { "tax_id": "305112233", "name": "...", "full_name": "...", "country": "UZ" },
    "lines": [ { "line_id": "<GUID строки 1С>", "item": { "id": "<GUID номенклатуры>" }, "expected_qty": "10" },
               { "line_id": "...", "item": { "id": "...", "code": "00-00004410", "name": "...", "unit_id": "<GUID единицы>" }, "expected_qty": "200" } ],
    "is_deleted": false } ] }
→ 200 { "results": [ { "index": 0, "id": "<ваш GUID>", "crm_id": "<uuid CRM>", "number": "GR-2026-00057", "version": 1, "result": "created", "created": { "partner": false, "items": ["00-00004410"] } } ] }
→ 207 если хотя бы один приход не принят

PUT /goods-receipts/{crm_id}                (один приход, те же поля)
→ 200 created | updated | unchanged | cancelled | cancel_requested
→ 409 stale_version | stale_update | receipt_posted | receipt_cancelled | line_has_serials | id_mismatch
→ 422 приход невалиден
```

Правила:
- **Поставщик только по ИНН.** `supplier.tax_id` обязателен (`tax_id_required`, ничего не создаётся). Неизвестный CRM поставщик создаётся с ролью «поставщик», включённой «Синхронизацией с 1С» и отметкой «требует проверки». Существующий партнёр с этим ИНН используется как есть.
- **Номенклатура по GUID 1С.** Для неизвестной позиции нужны `code`, `name` и известный `unit_id`; она создаётся с отметкой «требует проверки» и дополняется обычной выгрузкой `/items`. Позиции без серийного учёта проводятся только количеством.
- **Связь документов.** Сохраняйте `crm_id`, `number` и `version` из ответа. Поиск: сначала `crm_id`, затем ваш `id`; не найдено — приход создаётся. Присылайте имеющуюся у вас `version`: более старая — `stale_version`; более старый `updated_at` — `stale_update`. То же содержимое — `unchanged`.
- **Только до проведения.** Изменения принимаются, пока приход не проведён. Изменение проведённого прихода отклоняется (`receipt_posted`, `review_flagged: true`) и показывается кладовщику, который предлагает корректировку; данные, связанные с серийными номерами, никогда не перезаписываются.
- **Строки с серийными номерами** сохраняют номенклатуру и не удаляются (`line_has_serials`; из такого изменения ничего не сохраняется). Ожидаемое количество можно менять; если ожидается меньше, чем введено номеров, CRM показывает излишек, который кладовщик должен объяснить.
- **Строки с серийным учётом в результате:** `received` = число введённых серийных номеров, `damaged` = число отмеченных повреждёнными; для строк без серийного учёта — количества, введённые кладовщиком.
- **Удаление/отмена в 1С** (`is_deleted: true`): `cancelled`, если серийные номера ещё не введены, иначе `cancel_requested` (решает заведующий складом). Приход, отменённый в CRM, доступен 1С для получения как `goods_receipt.cancelled`.
- Одна транзакция на приход: непринятый приход не оставляет следов (ни полусозданного поставщика, ни номенклатуры). Идемпотентность по `batch_id`; до 50 приходов за запрос, до 500 строк в приходе.

## 7. Правила конфликтов и владение данными

| Данные | Владелец | Правило |
|---|---|---|
| Номенклатура, единицы, группы, цены, бух. коды, склады, остатки и себестоимость | **1С** | CRM их не меняет, только добавляет картинки и грузовые данные. |
| Клиенты, которые уже есть в 1С | **1С главнее** | Поля из 1С перезаписывают значения CRM. Если в CRM есть неподтверждённое изменение, CRM сохраняет заменённые значения в журнале для пользователя. |
| Новые клиенты, созданные в CRM | CRM до подтверждения | Дальше — 1С. |
| Серийные номера, гарантия, картинки товаров, грузовые данные CRM | **CRM** | 1С их не передаёт; если передать, они будут проигнорированы. Серийные номера 1С получает в `delivery.posted` (и в возвратах от клиентов). |
| Заказы, счета, договоры, реализации | **CRM** | 1С получает их и подтверждает своим GUID и номером. |
| Оплаты | обе стороны | CRM регистрирует оплаты, 1С подтверждает их через ack. Свои оплаты 1С передаёт через `POST /payments`. |

Сопоставление по ИНН (ред. 4, 2026-10-19):
- ИНН — единственный ключ. В CRM он уникален для партнёра, поэтому дубликат появиться не может: партнёр с этим ИНН обновляется (1С главнее), ваш GUID сохраняется как справочный, «Синхронизация с 1С» включается. Роли партнёра (клиент / поставщик / перевозчик) не меняются.
- Партнёра с таким ИНН нет: новый клиент создаётся, пока в CRM включена настройка «1С может создавать новых партнёров» (по умолчанию); иначе запись `skipped` с кодом `create_disabled`.
- Нет ИНН (филиалы, физлица, иностранные партнёры без ИНН): `skipped` с кодом `tax_id_missing`; такие партнёры не синхронизируются. Ведите их только в 1С или сначала укажите ИНН.
- `crm_id` и `id` по-прежнему принимаются для совместимости, но для сопоставления не используются. GUID, уже сохранённый у другого партнёра, даёт `conflict`.
- CRM отдаёт клиента в `GET /customers/pending` только если у него включена «Синхронизация с 1С» и есть ИНН. Для новых партнёров переключатель по умолчанию выключен; уже синхронизированные или стоявшие в очереди клиенты при обновлении включены.

## 8. Ошибки, повторы, идемпотентность

Все ошибки приходят в одном формате:

```json
{ "error": { "code": "validation_failed", "message": "...", "fields": { "batch_id": ["required"] }, "request_id": "..." } }
```

| HTTP | code | Что делать |
|---|---|---|
| 401 | `unauthenticated`, `signature_required`, `invalid_signature` | Проверить токен, часы и подпись. Не повторять вслепую. |
| 403 | `forbidden_ability`, `ip_not_allowed`, `https_required` | Ошибка настройки — к администратору CRM. |
| 404 | `not_found` | Неизвестный пакет (или пакет отправлен другим токеном). |
| 409 | `idempotency_key_reused`, `snapshot_mismatch` | `batch_id` повторно использован с другим телом. Для новых данных — новый `batch_id`. |
| 413 | `payload_too_large` | Разбить пакет. |
| 415 | `unsupported_media_type` | Указать `Content-Type: application/json; charset=utf-8`. |
| 422 | `validation_failed` | Исправить данные по полям `fields` (и `rejected` для ошибок в записях). |
| 429 | `rate_limited` | Подождать `Retry-After` секунд и повторить **тот же** запрос. |
| 503 | `integration_disabled` | Интеграция выключена в CRM. Повторить после `Retry-After`. |
| 5xx / сеть | — | Повторять с растущей паузой (5 с, 30 с, 2 мин, 10 мин) с **тем же** `batch_id`. |

**Идемпотентность.**
- У каждого push свой `batch_id` (UUID). Храните его вместе с исходящим пакетом в 1С, пока не придёт ответ 2xx.
- Повтор с тем же `batch_id` и тем же телом возвращает исходный ответ с заголовком `Idempotent-Replayed: true`. Повторного применения не будет.
- Заголовок `Idempotency-Key` необязателен; если вы его передаёте, он должен совпадать с `batch_id`.
- Подтверждения тоже идемпотентны: повторное подтверждение возвращает `already_applied`.

## 9. Примеры curl / Postman

Задайте переменные один раз:

```bash
BASE=https://crm.example.uz/api/v1/integration/1c
TOKEN=1c_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
SECRET=...   # только для токенов с подписью
```

Проверка связи (без подписи, из частной сети):

```bash
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/ping"
```

Запрос с подписью:

```bash
BODY='{"batch_id":"0b6f6a4e-2c1d-4f3a-9e8b-7d6c5b4a3f21","mode":"delta","sent_at":"2026-10-19T09:30:00+05:00","items":[]}'
TS=$(date +%s)
SIG=$(printf '%s.%s' "$TS" "$BODY" | openssl dgst -sha256 -hmac "$SECRET" -hex | sed 's/^.* //')
curl -s -X POST "$BASE/items" -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json; charset=utf-8" \
  -H "X-Timestamp: $TS" -H "X-Signature: sha256=$SIG" --data-binary "$BODY"
```

Документы — забрать и подтвердить:

```bash
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/outbox/pending?feed=orders&limit=200&cursor=0"
curl -s -X POST "$BASE/outbox/ack" -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  --data-binary '{"acks":[{"event_id":"b1c2d3e4-f5a6-4b7c-8d9e-0f1a2b3c4d5e","result":"applied","onec_guid":"f5a6b7c8-d9e0-4f10-a213-4d5e6f708192","onec_number":"ЦБ-00000881","posting_status":"posted","updated_at":"2026-10-19T11:06:00+05:00"}]}'
```

Остальные запросы (остатки, статус пакета, клиенты, оплаты) — в английской версии, раздел 9, и в Swagger.

**Postman.** Импортируйте `docs/openapi/1c-integration.json` (Import → File) — получится коллекция со всеми методами и примерами. Токен задайте на вкладке Authorization коллекции. Для подписи добавьте pre-request script с вызовом `CryptoJS.HmacSHA256(ts + "." + pm.request.body.raw, secret)`.

## 10. Примеры кода 1С (BSL)

Код рассчитан на платформу 8.3.14+ (`ХешированиеДанных` с SHA256 и `БуферДвоичныхДанных`). Тексты функций `HMAC_SHA256`, `ПодписьЗапроса`, `ВызватьCRM` (с повтором и паузами), `ВыгрузитьНоменклатуруВCRM` (пакетами по 500 записей) и `ЗагрузитьДокументыCRM` (выборка по курсору и подтверждение) приведены в английской версии руководства (`docs/integration-1c.md`, раздел 10). Код и комментарии там на русском, их можно копировать без изменений. Главное:

- Подписывайте ровно ту строку, которую отправляете: `ПолучитьДвоичныеДанныеИзСтроки(Метка + "." + Тело, КодировкаТекста.UTF8, Ложь)` — без BOM.
- Тело запроса устанавливайте так: `Запрос.УстановитьТелоИзСтроки(Тело, КодировкаТекста.UTF8, ИспользованиеByteOrderMark.НеИспользовать)`.
- Суммы передавайте **строками**: `Формат(Сумма, "ЧРД=.; ЧГ=0; ЧДЦ=2; ЧН=0.00")`.
- При повторе после сбоя отправляйте то же тело с тем же `batch_id`, сохранённое в очереди исходящих пакетов.
- Обрабатывайте 429 и 503 с учётом заголовка `Retry-After`; ошибки 4xx (кроме 429) не повторяйте — их нужно исправить.

## 11. Чек-лист запуска

- [ ] Рабочие токены созданы с минимальными правами, белым списком IP и (через интернет) с секретом подписи. Токены хранятся в 1С безопасно, дата окончания срока записана.
- [ ] Сервер 1С доверяет HTTPS-сертификату CRM. Часы синхронизированы (NTP).
- [ ] `GET /ping` проходит с рабочего сервера 1С.
- [ ] Первичная загрузка выполнена (единицы → группы → номенклатура → склады → полный снимок остатков → клиенты); все пакеты в статусе `processed`.
- [ ] Обмен клиентами проверен в обе стороны: созданный в CRM клиент забран и подтверждён с GUID; изменение из 1С отправлено.
- [ ] Каждая лента документов забрана и подтверждена хотя бы раз: заказ, реализация с серийными номерами, оплата, поступление. Проверено отклонённое подтверждение (его видно пользователям CRM).
- [ ] Проверена отправка оплат, включая `unmatched` и `is_deleted`.
- [ ] Проверен повтор: тот же `batch_id` возвращает `Idempotent-Replayed: true`.
- [ ] Регламентные задания включены и укладываются в 60 запросов в минуту.
- [ ] В разделе Настройки → Интеграции CRM время обмена по всем лентам свежее, предупреждений нет.
- [ ] Назначены ответственные за отклонённые подтверждения с обеих сторон; дата ротации токена — в календаре.
