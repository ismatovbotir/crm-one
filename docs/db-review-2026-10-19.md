# Database review - 2026-10-19 migrations (MySQL 8 focus)

Scope: every migration dated `2026_10_19_*` (015638 ... 165707), with the `customers -> partners` rename (101142), stock-off acts (155746), goods receipt 1C origin/status widening (143323, 143603, 143948), POA flags (164950), `payments.planned_order_id` (165707), plus a re-check of the 1C inbound batch migrations. Findings already in `docs/db-review-2026-10.md` (S3 ASCII GUIDs, F-06 activity retention, F-23 app code in migrations, 4.5 OTP hashing, ...) are only referenced, not repeated.

Mode: review only. No project file except this report was changed. The dev DB (SQLite) was only read (`migrate:status`, read-only PRAGMA queries).

**How MySQL was verified (not reasoned):** a throwaway MySQL **8.0.41** instance (OSPanel binaries, own datadir in the session scratchpad, port 3399, `utf8mb4_unicode_ci`) and a copy of `database/migrations` in the scratchpad. Steps: fresh `migrate` -> fix-and-retry on the copy until green, seed rows before 101142 (partners with/without GUID, outbox row, primary contacts, `customer`/`organization` morph rows, item price activity), migrate the 10-19 set, check data, `migrate:rollback` + re-`migrate` (diffed `SHOW CREATE TABLE partners`: identical), and finally `migrate:reset` of all 107 migrations (all `down()` pass, with the 101142 patch below). Online-DDL behaviour was probed with explicit `ALGORITHM=INPLACE, LOCK=NONE`. The instance was shut down afterwards.

- After fixing H-1..H-3 in a copy, **all 107 migrations run on MySQL 8.0.41 from zero, roll back completely (`migrate:reset`) and re-apply**; `SHOW CREATE TABLE partners` identical after up/down/up.

### 2.1 / 2.2 H-1..H-3 - fixing migrations that can never have run on MySQL

These three files are applied on the dev SQLite DB but **cannot have been applied on any MySQL** (they fail there). A new migration cannot help: a fresh MySQL install stops inside them. Options (needs the user's decision, because the rule is "never edit applied migrations"):

1. **Recommended:** edit them in place with changes that are no-ops for SQLite (explicit index names; MySQL-only branch in 101142). Already-migrated SQLite DBs keep the long index names - harmless - or converge with optional migration 2.8.
2. Squash now (`schema:dump --prune`) and regenerate the dump from MySQL - larger change, the earlier review put it in Phase E.

H-1 (015638) and H-2 (073630): pass the second argument, e.g. `$table->unique(['telegram_chat_id', 'telegram_contact_id'], 'tg_chat_members_chat_contact_unique');`, `$table->unique(['telegram_chat_id', 'message_id', 'kind', 'edit_date'], 'tg_messages_chat_msg_kind_edit_unique');`, `$table->unique(['organization_id', 'category_id', 'item_id'], 'catalog_visibility_rules_scope_unique');`. return new class extends Migration

        ['service_tickets', 'service_tickets_organization_id_foreign', 'service_tickets_partner_id_foreign', 'partner_id', 'partners', 'restrict'],
        ['catalog_visibility_rules', 'catalog_visibility_rules_organization_id_foreign', 'catalog_visibility_rules_partner_id_foreign', 'partner_id', 'partners', 'cascade'],
        ['requisitions', 'requisitions_organization_id_foreign', 'requisitions_partner_id_foreign', 'partner_id', 'partners', 'restrict'],
    ];

    public function up(): void
    {
        $this->swap(fromIndex: 1, toIndex: 2);
    }

    public function down(): void
    {
        $this->swap(fromIndex: 2, toIndex: 1);
    }

    private function swap(int $fromIndex, int $toIndex): void
    {
        if (DB::getDriverName() !== 'mysql') {
            return; // SQLite foreign keys have no names.
        }

        DB::statement('set foreign_key_checks = 0'); // existing, valid FKs: no re-validation needed, INPLACE
        try {
            foreach (self::KEYS as $key) {
                [$table, $column, $references, $onDelete] = [$key[0], $key[3], $key[4], $key[5]];
                $exists = DB::selectOne('select 1 from information_schema.referential_constraints where constraint_schema = database() and table_name = ? and constraint_name = ?', [$table, $key[$fromIndex]]);
                if ($exists === null) {
                    continue;
                }
                DB::statement("alter table `{$table}` drop foreign key `{$key[$fromIndex]}`, add constraint `{$key[$toIndex]}` foreign key (`{$column}`) references `{$references}` (`id`) on delete {$onDelete}, algorithm=inplace, lock=none");
            }
        } finally {
            DB::statement('set foreign_key_checks = 1');
        }
    }

### 2.6 M-2 - helper for FKs on large tables after go-live (mysql path, both engines)

```php
/** Adds a FK to a NEW nullable column without a table rebuild on MySQL (column is all NULL, no orphans possible). */
public static function addForeignOnline(string $table, string $column, string $references, string $onDelete = 'restrict'): void
{
    $name = "{$table}_{$column}_foreign";
    if (DB::getDriverName() !== 'mysql') {
        Schema::table($table, fn (Blueprint $t) => $t->foreign($column, $name)->references('id')->on($references)->onDelete($onDelete));
        return;
    }
    DB::statement('set foreign_key_checks = 0');
    try {
        DB::statement("alter table `{$table}` add constraint `{$name}` foreign key (`{$column}`) references `{$references}` (`id`) on delete {$onDelete}, algorithm=inplace, lock=none");
    } finally {
        DB::statement('set foreign_key_checks = 1');
    }
}
```

Put it next to `App\Support\SchemaChecks`. Use it only when the column was created in the same migration or verified orphan-free, because `foreign_key_checks=0` skips validation of existing rows.
